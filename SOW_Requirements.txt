 **Identity Portal - Complete Requirements Specification**

Below is the complete and concise requirements specification for Identity Portal , structured for inclusion in your documentation. It encapsulates all features, configurations, and technical details as defined across our discussions, ensuring a read-only web application for identity data access. The specification is optimized for clarity, minimal tokens, and adherence to best prompt engineering practices, retaining all aspects (role-based access, systems, mock/real toggles, UI, security) for local development. It is designed to guide incremental development across 10 phases, with no cloud or CI/CD components, and is suitable for documentation or AI-driven coding.

---

 **Overview**
Develop Identity Portal , a read-only web application for employees to view their own identity-related data from six systems: Ping Directory, Ping Federate, CyberArk, Saviynt, Azure AD, and Ping MFA, with limited search capabilities for Ping Directory (name/email) and Ping MFA (status/last event). Ops team members can view all users’ data across all systems for troubleshooting, including their own data and search capabilities. Support configurable roles (e.g., management) via JSON files. The app uses REST APIs (mock/real toggles), no database, and minimal dependencies. Built with React TypeScript (frontend) and Node.js/Express (backend), it features a responsive, accessible UI with developer-friendly styling (AI-determined, e.g., utility-first CSS). Deploy locally (`localhost:3000` frontend, `3001` backend) with mock mode default.

---

 **Identity Systems**
- **Ping Directory**: User attributes (e.g., name, email, department).
- **Ping Federate**: SSO details (e.g., last login, token status).
- **CyberArk**: Vault access (e.g., credentials status).
- **Saviynt**: Roles/policies (e.g., assignments).
- **Azure AD**: Profile/groups (e.g., memberships).
- **Ping MFA**: Status (e.g., enrolled devices, last event).

---

 **User Roles & Permissions**
- **Employee**: View own data from enabled systems; limited search for Ping Directory (name/email) and Ping MFA (status/last event) if enabled in config.
- **Ops**: View all users’ data across all enabled systems for troubleshooting; access own data and search if enabled.
- **Configurable Roles** (e.g., management): Defined in `roles.json` with permissions:
  - `own`: View own data.
  - `all`: View all users’ data.
  - `search`: Perform limited search (Ping Directory/MFA).
- **Fallback**: Undefined roles default to employee permissions.

---

 **Functional Features**
- **Data Viewing**:
  - **Initial View**: Display 10 key attributes per system (e.g., Ping MFA: status, enrolled devices) in cards.
  - **Details View**: “View Details” button expands to 20 attributes (includes initial, e.g., history, policies).
  - **Endpoints**: `/api/own-:system` (initial), `/api/own-:system/details` (details).
  - **All Users (Ops only)**: Filterable table (by system, name/email), pagination (limit 50, offset), row-click opens modal with tabs per system (20 attributes).
- **Search** (Employees/Ops if enabled): Input for name/email/ID; returns limited attributes for Ping Directory (name/email) and Ping MFA (status/last event) via `/api/search-employee/:query`.
- **Read-Only**: No write, update, or delete operations.
- **Error Handling**: Return 404 for disabled features, 403 for RBAC denials, user-friendly messages (e.g., “Feature not enabled”).

---

 **Authentication**
- **Mock Mode** (`useMockAuth: true`): Email/password form; role derived from email (e.g., `ops@company.com` → ops); issues JWT (24-hour expiry, stored in `localStorage`).
- **Real Mode** (`useMockAuth: false`): Simulate Ping SSO/MFA redirect; `/api/auth/callback` validates token, extracts role, issues JWT.
- **Toggle**: Configured in `features.json`; fallback to employee role for undefined roles.

---

 **Configurability (No Database)**
- **Configuration Files**:
  - **.env**: Define API URLs (e.g., `PING_DIR_URL=http://localhost:3001/mocks`), fallback credentials (e.g., `PING_DIR_API_KEY=mock-key`), CyberArk CCP settings (AppID, Safe), JWT secret, Ping SSO URL, logging settings (LOG_LEVEL=info, LOG_FILE=./logs/app.log).
  - **features.json**: Toggles for:
    - `credentialSource`: `env` (read from .env) or `cyberArkCcp` (REST fetch, stubbed locally).
    - `useMocks`: `true` (load mocks from `mocks/`), `false` (use real APIs or mock endpoints).
    - `useMockAuth`: `true` (email/password), `false` (SSO simulation).
    - `systems`: Enable/disable systems per role (e.g., `cyberArk: { employee: false, ops: true }`).
  - **roles.json**: Define permissions per role (e.g., `employee: { own: true, search: true }`, `ops: { own: true, all: true, search: true }`).
- **Credential Sourcing**: Fetch from `.env` or CyberArk CCP (stubbed as .env lookup in local mode); fallback to .env if CCP fails.
- **Application**: Edit configs and restart app to apply changes; validate configs on startup.

---

 **Mock Data Support**
- **Toggle**: `useMocks: true` loads JSONs from `mocks/`; `false` uses real APIs (mock endpoints locally via .env URLs).
- **Mock Files** (per system):
  - `<system>-initial.json`: 10 attributes (e.g., Ping MFA: status, enrolled devices).
  - `<system>-details.json`: 20 attributes (includes initial, e.g., history, policies).
  - `<system>-search.json`: 2-3 attributes for Ping Directory (name/email) and Ping MFA (status/last event).
- **All-Users Mock**: Array of initial JSONs for all users (Ops view).
- **Example**: Ping MFA initial (status: enabled, devices: 2); search (status: enabled, last event: 2025-09-19).

---

 **Technical Stack**
- **Frontend**:
  - React 18, TypeScript (strict mode).
  - Tailwind CSS (utility-first, AI-styled for developer-friendliness).
  - React Router (navigation: /login, /dashboard).
  - Native `fetch` (API calls, no Axios).
  - Hooks (`useState`, `useEffect`) for state management.
- **Backend**:
  - Node.js 18, Express (routing, middleware).
  - Winston (structured logging: info/warn/error, sanitized tokens, rotated logs: 5MB, 5 files).
  - Dotenv (environment variables).
  - Jsonwebtoken (JWT generation/validation).
  - Axios (backend-only, for real API calls).
- **Minimal Dependencies**: <50 total (e.g., react, express, winston, jsonwebtoken, axios); no Redux or Axios in frontend.
- **Proxy**: Frontend routes `/api/*` to backend (`http://localhost:3001`) via package.json (`"proxy": "http://localhost:3001"`).

---

 **UI/UX Requirements**
- **Design**:
  - AI-determined styling (e.g., utility-first CSS, blue/gray/red palette, clean typography: 24px headers, 14px body).
  - Components: Buttons (hover effects), inputs (focus states), cards (shadows, rounded corners).
- **Screens**:
  - **Login**: Centered card (400x500px); mock mode shows email/password form, real mode shows SSO button (stubbed locally).
  - **Dashboard**: Responsive grid (3-col desktop, 2-col tablet, 1-col mobile), sidebar (200px, collapsible on mobile).
    - **Employee**: Cards for own data (10 attributes, “View Details” for 20), search section (input/results table).
    - **Ops**: Adds all-users table (filters by system/name/email, pagination, modal with tabs for 20 attributes per system).
    - **Management**: Configurable via `roles.json` (e.g., own + search).
  - **Empty State**: Display centered message (e.g., “No systems enabled”) if no data available.
- **Interactions**: Smooth hover/focus transitions, loading spinners, error messages (e.g., red, fade-in).
- **Responsiveness**: Adaptive layout (3/2/1-col grid), mobile sidebar toggle (hamburger menu).
- **Accessibility**: ARIA labels, keyboard navigation, high contrast.

---

 **Security & Compliance**
- **Role-Based Access Control (RBAC)**: Enforce via `roles.json`; return 403 for unauthorized access (e.g., employee accessing all-users).
- **Authentication**: HTTPS in production (local optional), JWT validation, sanitized inputs (e.g., search queries via encodeURIComponent).
- **Logging**: Winston logs all access (role, system, timestamp), sanitizes sensitive data (tokens as `[REDACTED]`), rotates logs (5MB, 5 files).
- **Data**: No PII storage; mock data non-sensitive.
- **Rate Limiting**: 100 requests/min per IP (implemented via express-rate-limit).

---

 **Developer Experience & Local Deployment**
- **Setup**:
  - Prerequisites: Node.js 18+, npm 8+.
  - Folder: `identity-portal/` with `backend/` (server.js, configs) and `frontend/` (React app).
  - Run: Backend (`cd backend && npm install && node server.js`), frontend (`cd frontend && npm install && npm start`).
- **Maintenance**: Edit `.env`, `features.json`, `roles.json`, restart to apply; modular handlers (factory pattern for new systems/roles).
- **Testing**:
  - Unit: Jest (backend handlers, frontend components), React Testing Library (UI).
  - Integration: Test auth flows, mock/real toggles.
  - Manual: Verify login, data views, search, all-users table.
- **Extension**:
  - New System: Update `.env` (API URL/cred), `features.json` (enable system), `roles.json` (permissions), `mocks/` (JSONs), add handler (4 steps).
  - New Role: Add to `roles.json` with permissions.
- **Constraints**: No database; read-only; <50 dependencies; local focus (no cloud/CI/CD).
- **Documentation**: README.md with setup, run, testing, and extension guides.
